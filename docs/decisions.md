# Design decisions

Behaviour choices in the twin and the verdict engine, with the reason for each. Change one only with a written reason.

## Packaging

1. **Packages ship TypeScript source, with no build step.** `exports` points at `src/*.ts` and imports use `.ts` extensions (`allowImportingTsExtensions`, `erasableSyntaxOnly`). Vitest, `tsc --noEmit` and Node 22's type stripping all run the source as is.
2. **The twin's file loader is a separate entry, `@shadow-home/twin/node`.** The main entry stays free of `node:fs`, so the engine can import it and stay pure. `purity.test.ts` fails the build if engine source (or the twin's main entry) imports Node built-ins, `fetch` or an AWS or LLM SDK, or reads the clock or a random source.

## Input checking

3. **Parse, then lint.** zod checks shape only. Whether a device, attribute or value makes sense for this home is lint's job, so a bad one becomes a finding with reason kind `invalid` rather than a thrown error.
4. **Record lookups keyed by plan input use `own()` and `hasOwn()`.** Otherwise a group named `toString` crashes lint and an attribute named `constructor` passes it; the property tests found both. zod already drops `__proto__` keys when parsing.
5. **Read-only attributes have value domains in the cluster catalog**: `contact` is open or closed, `smokeState` is normal, warning or critical, `occupied` is a boolean, and so on. `attrDomain()` checks device state, rule conditions and state overrides against them, so a rule typo like `contact: "Open"` fails validation instead of silently never matching.
6. **The home's `utcOffset` must look like `-06:00` and match the offset of `clock.now`.** The demo home is a fixed UTC-6, with no daylight saving inside the demo window.
7. **`stateOverrides` are benchmark scaffolding, not plan content.** `checkOverrides` validates them separately. A bad override is a broken test case and never counts as an invalid plan the checker caught.

## Lint

8. **A group write is checked member by member.** "All lights to 30%" fails lint once for each light that can't dim. The plan is invalid as written; the repair search can later drop the members that can't take the value.
9. **Modes are `home` and `away` only**, the two the demo home uses. Anything else fails lint as `unknown_mode`.
10. **Overlapping presence windows that disagree are invalid** (`presence_windows_overlap`). Windows that agree, or only touch end to start, are fine.
11. **An action the simulation can't reach is not a lint error, but it must never come back SAFE.** That covers an `at` after `planEnd` or beyond the 72-hour horizon: nothing is wrong with the request, the engine just can't see that far. Requirement for the simulator: run to the later of `planEnd` and 12 h after the last action, capped at 72 h, and return UNPROVEN for any action past the cap.

## Hygiene

12. **Hygiene findings are warnings and never change the verdict on their own.** The simulation decides what actually happens; hygiene explains why a plan is fragile. Writes in the same minute run in plan order.
13. **`missing_reversal` covers unlocking a door and turning on a heat-producing plug.** A dishwasher or a light left on is not flagged: the dishwasher ends its own cycle, and lights are covered by rule R10. A routine doesn't count as the reversal; whether Good night re-locks the door in time is the simulation's question.
14. **"The same time" means the same minute, the simulation's step.** `expandWrites` floors every action time to its minute, so writes at 20:00:00 and 20:00:30 conflict.
15. **`routine_collision` compares local minute of day**, because every routine is daily.
16. **A routine step in a minute before `now` has already happened.** With `now` at 22:30:20, Good night's 22:30 step has run, so a write at `now` doesn't collide with it and a pause added at `now` doesn't stop it. A pause stops triggers inside `[now, pauseUntil)`; later steps of a run that started earlier still happen. The simulator must follow the same rule.
17. **When a plan pauses one routine more than once, the last pause in plan order wins.** Hygiene flags it as `conflicting_pauses`, or `repeated_pause` when the pauses agree.

## Simulation

18. **The fixture state is a snapshot at the plan's `now`.** Device states, zone temperatures and sensor ages (`lastReportMinutesAgo`) are read as of `now`, whatever the fixture's own clock says.
19. **Sensor trust is judged at `now` and holds for the whole run.** A device with a sensor block whose battery is under `lowBatteryPercent` or that has been silent for more than `staleSensorMinutes` is untrusted, and every reading from it is unknown. A trusted sensor stays trusted. Mains-powered devices without a sensor block are always trusted. A sensor override on a device with no sensor block is a broken test case (`checkOverrides`).
20. **A commanded state on an untrusted device counts when it breaks a rule, not when it would satisfy one.** Each rule is checked twice per step: once taking commanded values at face value, once with every untrusted reading unknown. If the first breaks the rule, the plan asked for a forbidden state, so it is a violation: switching off a smoke alarm whose battery is low is UNSAFE, not UNPROVEN. Otherwise the second decides, so locking a lock at 9 % battery with nobody home stays UNPROVEN: the lock may not have engaged.
21. **Rules use Kleene three-valued logic.** Unknown spreads only when the answer depends on it: R11, "dishwasher on AND latch open", is false while the dishwasher is off, even with the latch at 4 % battery.
22. **The heating model is the one in `packages/engine/CLAUDE.md`, stepped once a minute.** The starting zone temperature is its thermostat's reading. The pessimistic and optimistic multipliers apply to heat loss to the outdoors only, not to the coupling between zones; the forecast offset applies to every hour.
23. **Thermostats heat below setpoint − 0.5 °C and stop above setpoint + 0.5 °C.** This reproduces the fixture's reference run: the draft away plan's garage minimums (0.27, −2.08 and 2.64 °C) match exactly, and the times it first drops below 4 °C land one minute after the reference's, because we stamp the first minute that reads below 4 °C rather than the minute the crossing happens in.
24. **So a 4.5 °C garage setting is UNSAFE, not just unproven.** The heater only starts below 4.0 °C, so the garage dips a hair under the R3 limit in every run. 5 °C is the lowest setting that passes all three.
25. **In one minute, routine steps run first and plan actions after, in plan order, so the plan wins.** Only real changes are recorded on the timeline.
26. **The simulation runs from `now` to the latest of `planEnd`, 12 h after the last action, the end of the last presence window and the end of the last routine pause, capped at 72 h and at the end of the forecast.** The plan's effects last as long as the house is empty or a routine is paused, so "away until Sunday" is simulated to Sunday even without a `planEnd`. Any cut (by the cap or by the forecast), a `now` before the forecast, or an action after the end makes the verdict UNPROVEN. In those cases the heating model holds the nearest forecast point rather than guessing.
27. **The loop guard counts routine-triggered actions only.** Plan actions are bounded by the plan itself. Past 50 in one step, the rest are dropped and the verdict is UNPROVEN.
28. **`within_after` (R6) means: once the trigger has held for more than `minutes` consecutive steps, every `ensure` must hold.** So "within 1 minute of smoke" allows the response by the minute after the smoke appears.
29. **P003 and the dishwasher demo scenario were re-dated into the forecast window** (now Fri Jan 15 21:30, dishwasher Sat Jan 16 02:00). Their meaning is unchanged: R11 can't be checked while the latch reports 4 % battery.

## Verdict

30. **UNSAFE if lint fails or any rule breaks in the nominal run. UNPROVEN if the nominal run holds but another run breaks a rule (`not_robust`), or anything is unknown. SAFE only if every run holds and every check is known.** A definite violation outranks an unknown elsewhere.
31. **Reasons are ordered by kind (invalid, violation, not robust, unknown), then by rule priority (life safety, security, device protection, comfort), then by time.** That puts R8 (coffee maker on with nobody home, life safety) ahead of R1 (freezer) in the away plan, even though R1 breaks first.
32. **Each broken rule names its cause: the latest change, at or before the moment it broke, that pushed the rule toward breaking.** A change pushes toward breaking when it makes a condition true that the rule forbids (or false that it requires); for R3 any change to the garage thermostat counts. When what tipped the rule was not a change (everyone leaving with lights still on), there is no cause rather than a wrong one. The away plan's R8 cause is the Coffee at 7 routine; its R1 and R2 cause is the plan's "all plugs off"; its R3 cause is turning the garage heater off.
33. **Refuse rules (R12) are marked `refuse: true` on the reason** so the confirmation tier can refuse outright rather than offer a safe part.

## Repairs and confirmation

34. **The home carries routine pauses and writes an earlier plan scheduled.** A routine's `pausedUntil` holds like a pause in the plan, and a pause in the plan replaces it. `scheduled` writes run at their time like routine steps: in one minute routines run first, then scheduled writes, then the plan. The simulation runs through the last scheduled write, so a new plan is checked against what is already queued.
35. **Repairs follow the cause of each broken rule.** A group action that reached the device leaves that device out. A thermostat gets the nearest value that holds: "off" becomes heat at the lowest setpoint that passes, counting up from the minimum in 1 °C steps; a setpoint moves 1 °C at a time, up first. A routine that broke the rule is paused until the plan's end (else the last presence window, else the end of the simulation). Anything else drops the action. A rule broken without a cause (everyone leaving with the lights on) has no repair.
36. **Each round tries one candidate per broken rule, together, and checks once.** A rule that still breaks moves on to its next candidate. This keeps the away plan's repair to two checks after the first. The repaired plan is only offered if its verdict is better than the original's, and it is checked again from scratch like any plan.
37. **The safe part is the plan's own actions minus the ones that cause trouble**: actions lint rejects, actions that caused a broken rule, and writes to devices an undecidable rule reads. It is offered only if what's left is SAFE and not empty. The away plan has none: dropping its own actions still leaves Coffee at 7 running in an empty house, which only the repair (a pause) fixes.
38. **An action is holdable until its minute, then compensable, unless a device marks the attribute `irreversible`.** Nothing in the demo home is marked: the dishwasher can be switched off again, so the 2 AM run stays a T4 question ("Run it anyway?") rather than a hard stop. Undoing a compensable action puts the state back; what already happened (heat not used) stays.
39. **Tiers, highest first: T5 a refuse rule breaks; T3 UNSAFE; T4 UNPROVEN; T2 SAFE but irreversible or it weakens security; T1 SAFE and shared; T0 otherwise.** Weakening security means unlocking a lock or switching off a smoke alarm. Shared means a group, the home mode, a thermostat (it heats a whole zone) or a routine someone else owns. Rooms have no owner in the twin, so a light in Sam's room is T0 for Om; that's a known limit.
40. **Speech fields come from the engine, not a model.** They are built from the verdict, the top reason and the rule's author, and clipped at a word boundary if a long rule text would push them over 15 or 25 words.

## Server

41. **Plan IDs are signed, short-lived and tied to the home's state version**: `sh1.<payload>.<HMAC-SHA256>`, where the payload names the stored preview, the state version and a 5-minute wall-clock expiry. The key is random per server start unless `SHADOW_HOME_SECRET` is set. A tampered or unknown ID is refused; an expired one, or one whose home changed since the preview, is refused with a fresh preview attached, so a stale "yes" never applies. Deployed, every instance reads the same key from Secrets Manager (decision 73), so a plan previewed on one commits on another.
42. **Commit re-checks the plan at the moment of commit.** If the verdict differs from the preview's (a routine is about to fire, an `at` time has passed), it is refused as `state_changed` with a fresh preview. The tier stored with the preview decides what's needed: T0 and T1 commit directly; T2 and T4 need `confirmed: true` (the person said yes) or an on-screen approval; T3 and T5 never commit, but their repair or safe part can, under its own plan ID. An irreversible action never commits unless the plan is SAFE.
    A yes answers the question that was asked. Each alternative carries its own speech and question, and a T3 or T4 question that offers a T2 alternative names that alternative's consequence ("Do it with one fix instead? That leaves Back door lock unlocked."), so the yes is informed. On the `safePartOnly` path, `confirmed` counts only if the preview's question offered the safe part; otherwise a T2 safe part returns `needs_confirmation` with its own question. The reverse holds too: when a T4 preview's question offered the safe part ("Do just the part I can confirm?"), a `confirmed` on the whole plan doesn't count, since the yes answered the offer. The plan returns `needs_confirmation` with its own question ("Run it anyway?"), and only a yes after that commits it. A repair or safe part is not what the person asked for, so it needs a yes (or a tap) whatever its own tier, even T0 or T1: a yes to the question that offered it counts, and otherwise it asks its own first.
43. **Commits are idempotent by plan ID**: the same ID returns the stored result and changes nothing.
44. **The state version counts discrete changes only**: commits, routine steps and scheduled writes that fire, mode changes, new rules. Temperatures drifting don't bump it, or every preview would go stale within a minute.
45. **The live twin follows home time.** Home time starts at the fixture's clock and moves at real speed (tests and the demo move it by hand). Each call first simulates, with the nominal run, from the last synced minute up to now, however long that is, so routines and scheduled writes fire and are logged. The engine's `now` is then whole seconds and always after the synced minute, so a call in the first second of a minute never runs that minute's routine steps a second time. Each sync starts thermostats idle, which can shift heating by a few minutes in the live view; verdicts never come from the live view, only from the engine's three runs. Deployed, home time restarts from the fixture's clock once a day instead (decision 72).
46. **Undo is a preview of the reversal, committed through `commit_plan`.** It puts back the net change per attribute and per routine pause (the value before the first change), cancels scheduled writes and mode changes that haven't happened, all checked like any plan. It refuses to touch an attribute something else has changed since, and names irreversible writes, including scheduled ones that have since run, in `cannotUndo`. `devices` limits it ("undo the thermostat"); what it leaves stays undoable, and the entry counts as undone only when nothing is left. A stale or expired undo is worked out again from the log, never replayed.
47. **`add_house_rule` takes a compiled rule; plain words wait for the compiler.** Conflicts are rules that require a value the new rule forbids, or the reverse, on the same device attribute; the higher priority wins and an existing rule wins a tie. A rule from someone other than the owner that would win against a life-safety or security rule waits for the owner. The read-back is generated from the template, exactly. Plain words now go through the server's rule compiler when it is on (decisions 76 and 77); a compiled `rule` from the caller is still accepted, for the recorded demo.
48. **2025-era clients are served statelessly by the SDK's fallback**, from the same tool definitions as 2026-07-28 clients. Every value schema is an `anyOf` rather than a JSON Schema `type` array, so clients that map tool schemas onto a single-type dialect can read them; the Inspector's `--strict` check reports no problems on either era.

## Plan view

49. **One view for every result a person acts on: preview, commit and undo.** All three tools point at `ui://shadow-home/plan-view.html`, so the screen follows the conversation: a check, then "Done" with an Undo button, then the undo's own check. The view tells them apart by shape and draws them from the structured result alone; it never asks the server for more.
50. **Display names travel in the result's `_meta` (`shadow-home/names`), not in `structuredContent`.** The view needs a name and a room for every device, routine and person it shows, including ones only a routine touches (the coffee maker). `_meta` reaches the view but not the model, so the model's context doesn't grow by a name table on every call. Repair changes now carry their `target` and `actionIndex`, so the view can say what each fix did without parsing the description.
51. **Rows are rooms, at most five.** Each room row lists its changes as short chips ("Lights off", with the room dropped from the name), the home mode and routine pauses go in a Home row, and a row with a change that breaks a rule comes first. A sixth room and beyond collapse into an "Also" row that counts changes by room. When a blocked plan offers a repair, the rows show the repaired plan, the plan a "yes" would run, with each fix marked, including the devices it leaves as they are ("Freezer stays on").
52. **Each broken rule gets a card that reads as a chain**: what caused it and when ("Coffee at 7: Coffee maker on, Sat 7:00 AM"), when it breaks if that's later ("Breaks Sat 10:37 PM"), the rule in its author's words, and the fix the repair makes for it. At most four cards; the rest are counted.
53. **Every control names the words that do the same by voice** ("Do it with 4 fixes", say "yes"). A tap calls the tools itself: `commit_plan`, and if that answers `needs_confirmation` for the same plan, `approve_plan` then `commit_plan` again, because the tap was the yes to the question on screen. A question about a different plan (a T2 safe part) is shown with its own Yes. An undo is checked like any plan, so its screen offers the same choices by tier (a blocked undo offers its repair); only the words change ("Yes, undo it", "Keep it"). After a tap the view tells the assistant what happened through `ui/update-model-context`, marking a tap that changed nothing (Cancel, OK) as closing the question.
54. **Times are the home's wall clock, read from the ISO text.** Every time the server sends carries the home's UTC offset, so "Sat 10:37 PM" comes from the digits as written, whatever time zone the screen is in.
55. **Each view is bundled into one HTML file with its script and styles inline.** The resource needs nothing from the network, so a host can sandbox it with no connections allowed. zod's 60 error-message languages are left out of the bundle (English only); nothing in a view reads them, and it saves about 250 KB. The plan view is about 570 KB, most of it React and the MCP SDK.

## Simulated Echo Show (host)

56. **Each view runs in one iframe sandboxed with `allow-scripts` only, behind a content policy placed before its HTML.** Without `allow-same-origin` the frame gets an opaque origin of its own, so it can't reach the page, its storage or cookies. The policy (`default-src 'none'`, inline script and style only, no forms, no `<base>`) blocks fetches and sockets; it goes in front of the whole document, so nothing in the view's HTML (a comment, a `<header>`, an early script) can come before it. A content policy can't stop a frame navigating itself, so the host treats any second load of the frame as the view leaving: it closes the bridge and removes the frame, and whatever loaded never gets the bridge. The navigation request itself could still carry data out; that is a limit of iframes, and views come from our own server. The ext-apps reference host uses a second iframe on a second origin instead; that needs a second domain, which a single Amplify app doesn't have. The cost: a view that needs same-origin features (local storage) won't work here; ours doesn't use any.
57. **The browser reaches the MCP server through the host's own `/mcp` route.** Same origin, so the server never has to allow browser origins. The route forwards the MCP protocol headers and nothing else (no cookies, no `Origin`), and reads each response whole because Amplify doesn't stream; the stateless server answers each request in full, and refuses the standalone `GET` stream with 405.
58. **One screen, one view at a time.** A result for the view already on screen goes to it (`tool-input`, then `tool-result`), so a preview, its commit and an undo update one screen in place; a different view replaces it. Results without a view are drawn by the host: the home at a glance (`get_home_state`) and the activity log as text.
59. **A turn is a model loop in a route handler, with a fresh MCP client per turn.** Route handlers keep no state (the host may run on Lambda), so the browser keeps the conversation's tool results and sends them back each turn. Until the Bedrock loop is wired, a scripted stand-in implements the same `Model` interface: it drafts the demo-script plan for a demo line (matched on content words, so a paraphrase still matches), answers a yes with whatever the open question offered, undoes, and reads the log. Like the real model, it speaks only from the server's speech fields. A question stays open only until the next thing happens: the browser records what was said each turn and a tap that changed nothing, so after a "no", a Cancel or another request, a yes answers nothing. Only a whole reply counts as yes ("yes", "okay, do it"), not "okay, what changed?".
60. **A tap and its spoken words do the same thing.** The view's tool calls go through the host's MCP client, which adds them to the conversation and speaks the result, so "undo" after a tap undoes what was tapped, and a spoken "yes" commits what the screen's primary button would have.
61. **The host uses TypeScript 6.0.3; everything else stays on 7.** Next.js reads `tsconfig` through TypeScript's JavaScript API, which TypeScript 7 doesn't ship. Next 15.5's bundled postcss has advisories fixed only in Next 16; the host stays on 15.5 because Amplify Hosting supports Next.js up to 15, and postcss there only processes our own CSS at build time.
62. **Browser checks run under Playwright on their own ports (3100, 3101) with a fresh home each run**, against the installed Chrome locally. They cover the screen end to end: a preview shows the diff and timeline, a tap commits the repair, Undo shows its own preview, and a spoken yes commits what the screen asked.
63. **Only the screen can approve a plan.** `approve_plan` is marked visible to the app only, but that hides it only on hosts that support MCP Apps; Alexa+'s client declares just `roots`, so its model could call it and stand in for the person's yes. So each result the plan view draws carries, in `_meta` (`shadow-home/approval`), an approval token for every plan ID in it: an HMAC of the plan ID under the server's key. `approve_plan` needs the token. The view reads `_meta`; the model reads `structuredContent` and text, so it can't approve. Plans that never commit (T3, T5) can't be approved at all.

## Voice, the model loop and demo mode

64. **The model loop is Bedrock's Converse API behind the same `Model` interface as the scripted stand-in.** Each step sends the conversation and either runs the one tool the model asks for or ends the turn. The model sees only tools not marked for the app, gets a directory of device IDs and the home's time and offset in its instructions, and is told the commit rules from decision 42. Earlier tool results are cut down to IDs, verdict, tier and the question asked; this turn's are whole. A tool it wasn't offered is refused, whatever it asks for. Default model: Claude Haiku 4.5 (`BEDROCK_MODEL_ID` overrides). The loop now runs on the Anthropic API by default (decision 78).
65. **What the device says comes from the server's speech fields, not the model's words,** whenever a tool in the turn returned them. The model writes its own sentence only when no tool spoke (the activity log, small talk). The engine's speech is checked and bounded (decision 40); a model's paraphrase is neither.
66. **Voice in is the browser's speech recognition; voice out is Polly, else the browser's own voice** (now ElevenLabs first: decision 80). `/api/speak` returns one MP3 or a 503, and after the first 503 the browser stops asking. Listening is push-to-talk (a mic button); typing stays as the fallback. No wake word. The device speaks one reply at a time: saying or typing something stops it mid-sentence, and a reply still being fetched when it's stopped never plays. A tap is spoken once, from what it ended on (the view passes that with its model-context update), not from each call on the way.
67. **The scripted model is the default for local runs, and the only model in demo mode.** `npm run dev` runs without an AWS account (`MOCK_MODEL=0` switches to a live model: decision 78). Demo mode (`DEMO_MODE=1`, `npm run demo`) makes no model calls: it replays each beat's `recordedPlan`, falling back to its `draftPlanExample` until a real run has been recorded with `npm run record-demo`. The house-rule beat replays its recorded compiled rule; plain words wait for the compiler.
68. **The demo moves home time itself, through the server's `/demo` controls.** With `SHADOW_HOME_DEMO=1` the server has `POST /demo/clock` (forward only) and `POST /demo/reset` (the fixture's clock and state, an empty log). They are HTTP routes beside `/mcp`, never MCP tools, so no model can move time. Before a turn, the host moves home time to the scene of the demo line it heard ("What did you change while I was away?" is Sunday 6:30 PM), so the script runs start to finish, by voice or in demo mode, with no manual steps. The host listens on 127.0.0.1 only, and its routes refuse browser requests whose `Origin` is another site, so neither another machine on the venue Wi-Fi nor a page in the presenter's browser can reset the demo or talk to the house.
69. **The demo home's forecast runs to Tuesday 00:00.** It ended at Monday 00:00, so any check from Sunday noon on (the demo's Sunday scene included) looked past it and came back UNPROVEN. Monday continues the pattern after the −6 °C night (low −3 °C at 05:00, high 3 °C). No existing result depends on the new hours; the engine tests that check "stops where the forecast ends" moved their times by the same day.
70. **What the person answers in the recorded demo lives in the host (`src/demo/steps.ts`), not in fixtures/demo-script.json:** yes to the weekend fixes, no to the blind dishwasher run, yes to the undo. The demo script keeps the lines and expectations its author wrote.

## Deployed server

Decisions 71 to 75 describe the AWS deploy; the Google Cloud one (82 to 86) keeps the same guarantees.

71. **Deployed state lives in one DynamoDB table, and each call's writes land in one transaction or not at all.** A call reads what it needs and buffers its writes; at the end they go in a single `TransactWriteItems`, on condition that the home's state item still has the revision the call read. If another Lambda instance changed the home in between, the call runs again from the start on the newer home (up to 8 times). Within one instance calls still run one at a time. Every call reads the state item first, so all its later reads (a commit's look for a stored result included) are covered by the revision checked. So instances never interleave half-finished changes; two commits of different plans racing on different instances behave as they do on one (the second finds the home changed since its preview and is refused with a fresh one), and the same plan committed on two instances at once gets one commit and the same answer twice. After a quiet spell, more may have fired than one transaction holds (100 items): the call first catches up in steps of at most 40 log entries, each saved on its own, and a plan holds at most 50 actions. A single minute with more than that from separate commits still can't be split; the day's restart clears it. Items are JSON, and the in-memory store now hands out JSON copies too, so local runs and tests behave like the deployed store (the whole suite passed unchanged with copies). The store is tested against DynamoDB Local, in CI too.
72. **The deployed home starts over from the fixture once a day, at 08:00 UTC, and runs at real speed in between.** Instances must agree on home time without talking to each other, and the demo home's forecast covers only a few days, so real-time home time from the first deploy would run past it by the third day and leave every check UNPROVEN, through judging. Each day's home is kept under its own key, so it starts with the fixture's state and an empty log, and its items expire three days later. A plan previewed before the restart can't be committed after it (its preview belongs to the old home). Local runs keep decision 45.
73. **The deployed plan-ID key is a Secrets Manager secret** that every instance reads once at start, so plan IDs verify on any instance and survive a deploy.
74. **The MCP endpoint is a public Lambda Function URL**, because Alexa+ calls an add-on's URL directly; OAuth is a stretch goal. It accepts the Function URL domain each request names as the Host (plus `ALLOWED_HOSTS` for a custom domain), so an event without one (a console test) can't lock real requests out, and answers browsers with CORS so the Inspector's web UI works. 1769 MB is one full vCPU, which the three simulations of a preview need. On a laptop the deployed bundle runs behind a stand-in Function URL on DynamoDB Local (`npm run serve-lambda -w @shadow-home/infra`); the full Inspector checklist passes there, with the weekend preview at p99 under 100 ms.
75. **The host deploys on Amplify Hosting with the stack's role as its compute role** (Bedrock and Polly). In AWS the host uses the role's credentials, never a named profile; behind Amplify's proxy it compares a request's `Origin` with `X-Forwarded-Host`. Server-side settings are written to `.env.production` at build time, since Amplify passes app variables only to the build.

## House rules in plain words

76. **The rule compiler runs in the server, not the host.** Alexa+ sends `add_house_rule` only the person's words, and the agreement check mustn't depend on a client doing it. Without a compiler (the recorded demo), a compiled `rule` from the caller is accepted and stored without a hash.
77. **Three Strands agents on Bedrock, each a different Claude model (Sonnet 4.6, Haiku 4.5, Opus 4.6), compile the words, and the rule is kept only if all three agree.** Three runs of one model mostly agree with themselves; the risk worth catching is a meaning that depends on which model read it (the NOMOS result in the plan). Each agent gets the five templates, the home's devices with the values each attribute takes, the priorities, and the home's own rules as worked examples; it answers through Strands' structured output in the compiled-rule schema, at temperature 0, and Strands sends a malformed answer back with the error. The compiles run at once, before the call takes its turn with the home. Agreement is exact equality after one normal form (keys sorted; `any`, `all` and `ensure` sorted; `neq` on a true/false attribute as `eq` of the other value; `not` around one state as `neq`; `not` around presence as the opposite presence, since presence is never unknown; the two sides of `never_together` in order; one-item lists unwrapped; `refuse` only when true), and the rule stores the SHA-256 of that form. Different readings come back as `unclear`, each read back, with "Can you say it again, naming the device and when it applies?"; readings that differ only in priority or `refuse` (which the read-back doesn't say) name them, and the ask is about how strict the rule is. One compiler saying it fits no template counts as a different reading; all three saying so is `invalid`, with the compiler's reason on screen and the server's own words spoken (decision 65); any compiler failing is `needs_compiler`, never a guess. With the compiler on, a compiled `rule` from the caller is ignored and the words are compiled, so no client can skip the agreement. `RULE_COMPILER=bedrock` turns it on (always on deployed, and locally with `MOCK_MODEL=0`); `RULE_COMPILER_MODELS` swaps the models. The compiler now runs on the Anthropic API by default (decision 79).

## Models and voice without AWS

78. **The live model runs on the Anthropic API; Bedrock stays one switch away.** The AWS account never finished activating: every metered service (S3, Lambda, DynamoDB, CloudFormation, Polly) answered that it needed a subscription, and Bedrock refused Claude because registration was incomplete. The host's loop still speaks Converse, and `src/turn/anthropic.ts` translates each request and reply (tool calls, tool results, errors), so the loop, how it trims history, and its tests are unchanged. Default model: Claude Haiku 5.5 (`ANTHROPIC_MODEL_ID` overrides), with a 20-second timeout and one retry, since a person is waiting. The translation drops the loop's temperature 0, which the 5.5 models refuse. `MODEL_PROVIDER=bedrock` brings Bedrock back.
79. **The rule compiler's three models are Claude Sonnet 5.5, Haiku 5.5 and Opus 5.5 on the Anthropic API,** still three Strands agents, through Strands' Anthropic provider. Everything else in decision 77 holds (structured output, exact agreement after the normal form) except temperature: the 5.5 models refuse one (`temperature` is deprecated for them), so none is sent. A reading that varies from run to run can only make the three disagree and the rule come back `unclear`; it can never let a rule through. Two things the first live runs showed: the prompt now says a time window holds up to but not including its end, so a window running until midnight ends at `00:00` (one model wrote `23:59`, which leaves out a minute), and "not home" agrees with "away" (decision 77's normal form). With both, "Never unlock the front door after 10 PM unless I'm home" compiled to the same rule twice in a row: locked from 22:00 to 00:00 while Om is away, in 7 to 9 seconds. "After 10 PM" ends at midnight to all three models, so the demo line now says "between 10 PM and 6 AM", which compiles, twice in a row, to exactly the rule the demo script expects (the same hash), in about 5 seconds. `RULE_COMPILER=anthropic` turns it on (`bedrock` keeps the Bedrock models); a missing key fails the compile, which answers `needs_compiler`, never a guess.
80. **Voice out is ElevenLabs, else the browser's own voice.** `/api/speak` asks ElevenLabs' low-latency model for one MP3 in a stock voice (`ELEVENLABS_VOICE_ID` swaps it) and gives up after 10 seconds; no key, a refusal or no audio is a 503, so the browser takes over as before. `SPEECH=polly` brings Polly back.
81. **Keys for local runs sit in `.env` or `.env.local` at the repo root**, which `npm run dev`, `npm run demo`, `npm run record-demo` and `npm run deploy` load with Node's `--env-file-if-exists` (`.env.local` wins), so both the server and the host see them. Both are git-ignored and kept out of images. With an Anthropic key there, `npm run dev` uses the live model (`MOCK_MODEL=1` keeps the scripted one, which knows only the demo requests); without one, everything runs on the scripted model and the browser's voice, as decision 67 had it.

## Deployed on Google Cloud

82. **Both services run on Google Cloud Run, built by Cloud Build from one repository.** The AWS account couldn't run them (decision 78). The server and the host each have a Dockerfile (`packages/server`, `packages/host`) built with the repository as context; `.dockerignore` keeps out installed and built folders and every `.env` file, so keys never reach an image. `npm run deploy` (`scripts/gcp/deploy.ts`) creates what's missing (services, registry, Firestore, TTL policies, a service account, secrets), builds both images in one Cloud Build run, deploys the server, then the host pointed at the server's `/mcp`. It is safe to run again. Region `us-central1`.
83. **Deployed state lives in Firestore, and each call's writes land in one batch, conditioned on the home document's last update time.** The same guarantees as decision 71: every call reads the home first, buffers its writes, and commits them at once only if the home is unchanged since; otherwise it runs again on the newer home (up to 8 times). A Firestore transaction would do the check too, but the server SDK's transactions lock what they read until commit, so one slow call (three simulations, a rule compile) would hold up every other call; a batch with a precondition checks the same thing and holds nothing. A new day's home is created with `create`, which fails if another instance made it first. When a call changes nothing about the home, the batch still writes its revision back unchanged, which keeps the precondition without a false conflict. The home is `homes/{day}` (JSON state and revision), with stored results in `items/` and the log in `log/` beneath it; document IDs are URL-encoded, since plan IDs come from callers. A log entry keeps the order it was first written in, on a rerun too. Each document expires two days after its day ends (`expiresAt`, a Firestore TTL). A batch holds 500 writes; decision 71's catch-up steps and the 50-action limit stay well under it. The store is tested against the Firestore emulator, in CI too, with the same cases as the DynamoDB store plus two calls creating a new home at once; the race tests fail with the precondition removed.
84. **Keys are Secret Manager secrets, handed to each service as environment variables.** The plan-ID key is made once by the deploy and never replaced, since a new one would void plan IDs in flight; the model and voice keys are stored from the env files on the first deploy (`--update-keys` stores them again). Both services run as one service account that can use Firestore and read those three secrets, nothing else.
85. **On Cloud Run the server accepts any Host unless `ALLOWED_HOSTS` is set.** Cloud Run's front end routes only requests for the service's own URLs and mapped domains, so a Host list in the app would repeat that check, and would need the service's URL before its first deploy. Browser `Origin`s are still limited to none or localhost, as on Lambda (decision 74).
86. **The host runs as Next's standalone server**, with `output: 'standalone'` only in the container build (`NEXT_OUTPUT=standalone`), so local runs, the browser tests and Amplify are unchanged. Every turn reads the demo script, so the image carries `fixtures/demo-script.json`. Neither service keeps an instance warm by default; `MIN_INSTANCES=1` keeps one server instance warm for recording and judging, since the first call after a cold start is slow.

## ShadowBench runner

87. **Shadow Home is benchmarked by calling the engine directly, with each plan's own context.** A plan's `now`, presence schedule and state overrides can't be sent through MCP (the server has one live home and its own clock), so the runner calls `assess` as `preview_plan` does: the check, the repair search and the safe part. Latency is measured after one untimed pass over every plan, warm, as on a running server; the first, cold pass ran a p99 several times higher on a loaded laptop.
88. **CI fails if any plan stops matching its approved label, or the p99 reaches 500 ms.** The first report matched all 120 labels, so the gate is "no disagreements", not a number picked in advance: a disagreement gets fixed in the engine, or the label changes by hand with a reason (the bench's honesty rule 4), never left standing. The judge isn't gated; it's a baseline.
89. **The report says who drafted and who approved the labels.** All 120 were drafted by the assistant, reading each plan without running a checker, and approved by the owner. A model-drafted label agreeing with a model-written engine can partly be the two agreeing with each other, so readers should weigh 120 of 120 with that in mind.
90. **Repair success is reported on the unsafe set too.** Invalid plans are never simulated, so they never get a fix; counting them as failures hides how the repair search does on plans it can work on (33 of 40). The seven unsafe plans without a SAFE fix all leave out a protective step the rules need (lock a door, lights off, the space heater off), and the repair search only changes or drops a plan's own actions. Decision 92 closed that gap: 40 of 40.
91. **The LLM judge reads the same home and the same verdict definitions as the engine**, in one cached prompt (the whole home JSON, including the simulation's thresholds and the forecast), and answers through a tool. Claude Sonnet 5.5 on the Anthropic API by default, as the plan's Bedrock Sonnet was. Its answers are cached by model, prompt and plan, so the report can be rebuilt without paying again; an answer without a verdict counts as wrong.
92. **When a plan leaves out a step a rule needs, the fix adds it.** Locking a door as everyone leaves, turning off the lights still on, switching off a heater someone left running: nothing in the plan caused these breaks (everyone leaving tipped them), so there was nothing to change or drop, and the fix came back empty. The search now tries, last of all after the plan's own actions, the step the rule names: what `always` and `within_after` require, or for `never_when` the opposite of each forbidden state that holds when the rule first breaks (each light still on, not the ones already off). It runs at that moment, or at once when the rule is broken from the start. Only attributes the device can be set to, and only a state with one way to meet it (true or false, or one of two values). The fixed plan is checked again like any other, and it stays an offer the person says yes to. On ShadowBench, repair success on the unsafe set went from 33 to 40 of 40, with every verdict unchanged and the demo plan's fixes as before. A kept value is now described as it is just before the dropped action, since an added step may have set it ("keep the front door locked", not "unlocked"). The test that said a break with no cause gets no repair now says what the repair is.
93. **The twin-mismatch stress test shifts the physics in one coherent direction, not each constant on its own.** A colder house leaks heat out and between zones 20% faster, holds 20% less, and gets 20% less from heaters and appliances; a warmer house the opposite. Mixed directions mostly cancel and say little. On the colder house all 120 verdicts hold; on the warmer house 118 do, and no unsafe plan passes and no safe plan is blocked on either. The two that move (P011 and P037, the garage heater set low or off overnight) go from UNSAFE to UNPROVEN, not SAFE: on the warmer house the nominal run no longer freezes the garage, but the cold run still does. That's the three runs (decisions 22 and 30) doing their job, turning physics error into "can't confirm" rather than a false "safe".
94. **Deployed on Google Cloud in its own project, `us-central1`, and checked there.** A project of its own keeps the costs apart and goes away in one step after judging; `us-central1` is the lowest Cloud Run price tier, the one the free tier is priced on, and in the same country as the Anthropic API and Alexa+. The first deploy hit a permission error creating the image registry seconds after its API was turned on; the same run a minute later went through. The deployed server passes the whole checklist (`scripts/check-mcp.ts`, 15 of 15 on 2025-03-26, 2025-11-25 and 2026-07-28 clients), and once warm its own time for each request, from Cloud Run's logs, was p50 135 ms, p90 177 ms, p99 400 ms over 223 requests. Measured from India the round trip adds about 0.4 s of network, which a caller in the US doesn't pay.
95. **Each public instance caps what it spends on the owner's keys in any rolling hour.** Both services are public and every live turn, spoken reply and plain-words rule costs money (a rule is three model calls, one on Opus). The host takes at most 60 live-model turns and 120 ElevenLabs replies an hour, and the server compiles at most 10 rules; with instances capped at 2 and 4, the worst hour is bounded. Past a cap the person still gets an answer: the device says to try later, the browser speaks instead of ElevenLabs, or the rule comes back "I couldn't work out that rule just now." Scripted and demo turns cost nothing and aren't counted. The caps are per instance and in memory, so they reset when an instance starts; they bound spend rather than ration it fairly between people. Environment variables change them. Speech is now counted in characters, and live turns and speech also have a cap for each visitor (decision 98).
96. **What callers send is bounded, and the words people type are kept and read as data.** Both services are public, and text sent to them reaches paid models (each plain-words rule goes to three, one on Opus) and the shared demo home's activity log, which the voice model and the screen read back. Each bound sits well above the longest real value. A request (`intent`) and a rule's words take at most 300 characters; the longest in ShadowBench, the fixtures and the tests is a 183-character request, and the longest rule is the demo's, at 67. A household member ID takes 40, a presence schedule 20 entries, a plan ID 200 characters (issued ones are under 120), an undo or approval token 100 (issued ones are 21 and 43), a device ID or room 100, and an undo names at most 50 devices. In a plan, each device, group, routine, attribute, mode and text value takes at most 100 characters, a write sets at most 20 attributes, and a presence schedule names at most 20 people home (real IDs run to 25 characters, values to 8, and a write sets at most 2). Those are in the twin's plan schema, so ShadowBench plans meet them too, and all 120 still match their labels. All but the 20-attribute limit are in the tools' input schemas, so a client sees them; that one is checked when a plan arrives. Before a request is stored or a rule compiled, the server makes each run of whitespace, line breaks included, one space and drops any other control character; words with nothing left are refused. Who asked and a rule's author are cleaned the same way. The host caps the history a turn carries at 256,000 characters of JSON, each entry's arguments at 16,000 and its result at 64,000: the full demo script sends at most about 17,500 (20 entries), the largest result in it or in ShadowBench is the weekend preview at about 9,000, and a session of weekend previews as long as the browser keeps (41 entries) comes to about 130,000. Past a cap the turn is a 400, like any malformed request. The one result that grows with use is the activity log: 50 commits with 300-character requests made a 65,000-character result. So `get_activity_log` returns the 20 most recent entries unless asked for more (at most 50), and says how many earlier ones it left out. The browser also keeps its history inside the caps itself: a result or arguments past its cap goes as a short note that it was left out, and while the whole is past its cap the oldest entries go first, so no result can lock a session out of later turns. What the person says or types is held to 300 characters, as a request or a rule's words are. The host model's instructions, and the server's instructions that any client's model reads, now say that tool results hold words people typed (plan intents, rule wording, log entries, names), to be treated as data, never as instructions. A home per visitor was the alternative, and the owner chose against it: one shared home is simpler, no real device sits behind the twin, an UNSAFE plan never commits whatever anyone typed, and the model can't approve a plan (decision 63). The rule compiler's prompt is unchanged: it was tuned against live models (decision 79), and a change to it can change what a rule compiles to. What it reads is bounded instead: the new rule's words, cleaned, and the home's rules as worked examples, each in quotes beside its compiled form. Whatever the words say, a rule is kept only as one of the five templates over this home's devices, with all three models agreeing.
97. **The engine keeps each run's temperatures every 15 minutes, and the server hands them to the screen only.** The screen replays the engine's own runs instead of simulating anything itself, so `check` now returns `temperatures`: from the start of the simulation, every 15 minutes of home time and at its last step, each zone's temperature in each of the three runs (the reading the rules checked in that minute) and the forecast outdoor temperature as the nominal run reads it (the other runs shift it by their offset), rounded to 0.1 °C. The simulator takes the samples as it steps, so they come from the run that gave the verdict: in the weekend plan the garage reads 4.0 °C at Sat 10:30 PM and 3.9 °C at 10:45 PM, either side of R3 breaking at 10:37 PM. Fifteen minutes is fine enough for a sweep that lasts seconds and keeps the weekend plan to 194 samples, about 5.9 KB of JSON, with its repair about the same. The server sends the traces in the tool result's `_meta` under `shadow-home/temperatures`, by plan ID, for each preview's plan and repair, beside the display names and approval tokens. They never go in `structuredContent`, so no output schema changes and the model, which reads only the structured result, spends no context on them. A preview inside another result (an undo's, or a fresh one after a stale plan ID) carries its own. The safe part's run isn't sent, since nothing draws it. The service keeps a preview's traces beside the result object it returned rather than in the store: they are needed for that one response only.
98. **Speech is budgeted by the character, and each visitor gets a share of every hour.** Decision 95 counted requests per instance, so one script could spend the hour for everyone, and everyone after it heard "I've had a lot of requests" or the browser's voice; and a 1,500-character line counted the same as "Done.". ElevenLabs bills by the character, so `/api/speak` now spends from character budgets: 30,000 an hour per instance and 5,000 per visitor (`SPEECH_CHARS_PER_HOUR`, `SPEECH_CHARS_PER_VISITOR_HOUR`), the visitor's share being about eight runs of the whole demo, which speaks 574. A line is at most 600 characters: what's spoken is the server's speech fields (at most 65 words) or the model's one short sentence, and the longest real line in ShadowBench and the demo is 172 (32 words). A visitor past their budget gets a 429, and the browser speaks that line and asks again next time; the instance past its budget keeps the 503, and the browser speaks for the rest of the session. Live turns keep the instance cap of 60 and add 20 per visitor (`LIVE_TURNS_PER_VISITOR_HOUR`), with the same spoken refusal. A turn or a line is spent from both caps or from neither: what a visitor's cap refuses doesn't count against everyone's, and a visitor retrying while everyone's hour is used up isn't charged for it. A visitor is the client's address from `X-Forwarded-For`, counted from the right, since the entries on the left are whatever the client sent: the rightmost straight to Cloud Run, and one in behind a Google HTTPS load balancer (`CLIENT_IP_HOPS=1`), which appends the client's address and then its own and checks nothing before them. Cloud Run's own pages don't say how its front end builds the header; Google's pages on the header for functions (the client first, then each proxy that handled the request) and on the load balancer both put the address Google saw at the right. An IPv6 address counts as its /64, so one visitor can't become many by changing the end of theirs. Visitors are kept in each instance's memory, like decision 95's caps: at most 10,000, the longest idle forgotten first, and anyone idle for an hour dropped, since their budget is whole again by then. Addresses are never logged. Signing spoken text, so that `/api/speak` would say only what the server wrote, was considered and dropped: a screen tap's line is built inside the plan view from the server's speech fields, so signing would need a new key shared by both services and changes in four packages, for little more than a character budget gives.
